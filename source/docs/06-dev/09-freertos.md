## 1. 一句话理解

**FreeRTOS 把听声音、网络处理、播放和舵机动作交给不同任务，通过事件与队列配合。** 有多个任务不代表所有功能都能无条件同时运行，还要看音频状态、队列和取消逻辑。

## 2. 几个词就够了

| 词 | 奶龙里的例子 |
|---|---|
| 任务 | 采集音频、编码解码、驱动舵机、播放本地笑声 |
| 优先级 | 调度时谁先得到执行机会，以源码创建参数为准 |
| 队列 | MCP 把动作请求交给动作任务 |
| 事件 | 唤醒、语音停止或其他任务请求主循环处理 |
| 取消代次 | 区分旧任务与新请求，避免取消后继续补入旧音频 / 轨迹 |

## 3. 一次动作

1. 云端调用 `self.otto.action`，例如 `action="swing"`。
2. 回调解析参数并排队，不在网络回调中慢慢转舵机。
3. 动作任务执行 `otto_movements.cc` 中的方法，完成后归位。
4. 最新停止候选在循环、插值和等待中检查取消，清理排队动作。

实际能否及时听到“停下”还取决于识别、音频模式和现场噪声，不能只凭存在多个任务就认定通过。

## 4. 一次笑声或组合动作

`nailong_actions.cc` 的后台任务处理本地笑声。它先等已有音频排空，播放时切换场景图，等实际播放结束再完成 MCP 回调。

`laugh_walk` 在一次请求中协调笑声任务和动作任务。需要两项都结束；忙时拒绝整个组合，避免先排队行走却已经开始笑。完整效果仍需实测。

## 5. 写代码记住三条

| 规矩 | 原因 |
|---|---|
| 耗时工作交给任务，使用有界队列 | 不阻塞网络与主循环，不无限积压 |
| 状态变更沿用 `Schedule` 和应用事件路径 | 避免多个任务直接抢着改状态 |
| 长循环、插值和等待处理取消 | 停止后不能继续写旧轨迹或补旧音频 |

任务名、栈和优先级以当前 `audio_service.cc`、`otto_controller.cc`、`nailong_actions.cc` 为准，不套用旧版本的任务表。

## 6. 常见报错

| 日志 | 先查什么 |
|---|---|
| `stack overflow` | 对应任务栈是否足够 |
| `Task watchdog` | 是否有不让出 CPU 的循环或长阻塞 |
| `Guru Meditation Error` | 用匹配构建的 `idf.py monitor` 查看回溯 |
| USB 串口突然断开 | 重新连接并抓完整启动日志，不能仅凭断开判断固件崩溃 |
